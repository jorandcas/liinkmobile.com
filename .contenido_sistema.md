## 📋 RESUMEN EJECUTIVO

**Nombre del Sistema:** DN (Distribuidor Number) Verification System - Multitenant Edition para Movistar

**Versión:** 2.0.0 (MVP Multitenant)

**Propósito:** Validar números de teléfono contra el API de inscripción de distribuidores de Movistar con arquitectura multitenant completa

**Arquitectura:** Sistema multitenant con bases de datos PostgreSQL separadas por tenant para máximo aislamiento

**Funcionalidades Principales:**
- ✅ **Sistema Multitenant completo** con BDs separadas por tenant
- ✅ **Validación individual de teléfonos**
- ✅ **Validación por lotes (JSON)**
- ✅ **Validación masiva desde CSV** con progreso en tiempo real (SSE)
- ✅ **Gestión de campañas de validación**
- ✅ **Panel web con interfaz de usuario**
- ✅ **Autenticación JWT profesional** con jsonwebtoken
- ✅ **Autorización por roles** (SuperAdmin, Tenant Admin)
- ✅ **Cifrado AES-256-GCM** para API Keys
- ✅ **Sistema de auditoría completo**
- ✅ **Cambio obligatorio de contraseña** en primer login
- ✅ **Bloqueo de cuentas** por intentos fallidos
- ✅ **UI SuperAdmin** para gestión de tenants
- ✅ **Landing page de marketing** con integración WhatsApp

## 🗄️ ARQUITECTURA DE BASE DE DATOS

### Multitenancy con BDs Separadas

**Estrategia:** Máximo aislamiento con bases de datos PostgreSQL separadas por tenant

```
PostgreSQL Server
├── bd_superadmin          # BD principal
│   ├── tenants            # Tabla de tenants + superadmin
│   └── audit_logs         # Auditoría global
│
├── tenant_govi            # BD del tenant Govi
│   └── validaciones       # Validaciones de Govi
│
├── tenant_mundoelite      # BD del tenant Mundoelite
│   └── validaciones       # Validaciones de Mundoelite
│
└── tenant_{nombre}        # BD de cada tenant
    └── validaciones       # Validaciones del tenant
```

### Tabla Principal: `tenants`

```sql
CREATE TABLE tenants (
  id SERIAL PRIMARY KEY,
  nombre VARCHAR(100) UNIQUE NOT NULL,
  email VARCHAR(255) UNIQUE NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  bd_name VARCHAR(100) UNIQUE NOT NULL,
  api_key_encrypted TEXT,                    -- NULL para superadmin
  api_status VARCHAR(20) DEFAULT 'pendiente', -- 'pendiente' | 'valida' | 'invalida'
  tenant_status VARCHAR(20) DEFAULT 'activo',  -- 'activo' | 'suspendido'
  role VARCHAR(20) DEFAULT 'tenant_admin',     -- 'superadmin' | 'tenant_admin'
  must_change_password BOOLEAN DEFAULT true,   -- Cambio obligatorio al primer login
  last_login_at TIMESTAMP,
  failed_login_attempts INTEGER DEFAULT 0,
  locked_until TIMESTAMP NULL,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);
```

### Tabla de Auditoría: `audit_logs`

```sql
CREATE TABLE audit_logs (
  id SERIAL PRIMARY KEY,
  tenant_id INTEGER REFERENCES tenants(id),
  user_email VARCHAR(255) NOT NULL,
  action VARCHAR(100) NOT NULL,
  details JSONB,
  ip_address VARCHAR(45),
  created_at TIMESTAMP DEFAULT NOW()
);
```

### Tablas de Tenant: `validaciones`

Cada tenant tiene su propia BD con tabla de validaciones:

```sql
CREATE TABLE validaciones (
  id SERIAL PRIMARY KEY,
  telefono VARCHAR(20) NOT NULL,
  resultado JSONB NOT NULL,
  origen VARCHAR(10) NOT NULL,
  exitoso BOOLEAN NOT NULL,
  created_at TIMESTAMP DEFAULT NOW()
);
```

## 🔄 FLUJO DE DATOS

### Flujo de Creación de Tenant (SuperAdmin)
```
1. SuperAdmin login → JWT token
2. POST /api/superadmin/tenants con datos del tenant
3. SuperAdminController.createTenant()
4. TenantService.createTenant():
   a. Validar nombre único
   b. Validar email único
   c. Validar API Key (test request a DN)
   d. Crear BD separada para tenant (tenant_{nombre})
   e. Crear tabla validaciones en BD del tenant
   f. Cifrar API Key con AES-256-GCM
   g. Hashear contraseña con bcrypt
   h. Insertar tenant en BD superadmin
5. Registrar en audit_logs
6. Retornar tenant creado (sin API Key descifrada)
```

### Flujo de Login (Universal)
```
1. Usuario ingresa email/password
2. POST /api/auth/login
3. AuthService.login():
   a. Buscar usuario por email en BD
   b. Verificar si está activo (tenant_status)
   c. Verificar si no está bloqueado (locked_until)
   d. Verificar contraseña con bcrypt.compare()
   e. Si falla:
      - Incrementar failed_login_attempts
      - Si >= 5, bloquear cuenta (locked_until = now + 15min)
      - Retornar error
   f. Si éxito:
      - Resetear failed_login_attempts a 0
      - Actualizar last_login_at
      - Generar JWT token con userId, email, role
4. Retornar token + datos del usuario (sin password_hash)
5. Cliente guarda token en localStorage
6. Requests subsiguientes incluyen header: Authorization: Bearer {token}
```

### Flujo de Validación de Teléfonos (Tenant)
```
1. Tenant login → JWT token
2. POST /api/validate/single con teléfono
3. authMiddleware verifica token → Extrae tenant_id del JWT
4. DistribuidorController.validarIndividual()
5. DistribuidorService.validarMultipleAmbientes():
   a. Obtener API Key descifrada del tenant (getTenantApiKey)
   b. Por cada ambiente seleccionado:
      - ApiClient.get() con API Key del tenant
      - 5 segundos de delay entre ambientes
   c. Guardar resultados en BD del tenant (tenant_{nombre})
6. Resultados retornados al cliente
7. Opción de guardar como campaña en BD del tenant
```

### Flujo de Validación Masiva CSV (Tenant)
```
1. Tenant login → JWT token
2. Usuario sube archivo CSV
3. Multer guarda archivo en uploads/
4. POST /api/validate/bulk con FormData
5. DistribuidorController.validarMasiva()
6. DistribuidorService.validarMasiva():
   a. Leer CSV con csv-parser
   b. Abrir canal SSE con cliente
   c. Por cada teléfono:
      - Validar en ambientes seleccionados
      - 5 segundos delay entre requests
      - Enviar progreso via SSE
   d. Al completar:
      - Enviar resultado final via SSE
      - Auto-crear campaña en BD del tenant
7. Cliente cierra conexión SSE
```

### Flujo de Cambio de Contraseña (Primer Login)
```
1. Usuario intenta acceder a /dashboard.html
2. passwordChangeMiddleware verifica must_change_password
3. Si es true:
   - Redirigir a /cambiar-password.html
   - Mostrar modal/aviso de cambio obligatorio
4. Usuario ingresa contraseña actual + nueva
5. POST /api/auth/change-password
6. AuthService.changePassword():
   a. Obtener usuario y password actual
   b. Verificar contraseña actual con bcrypt.compare()
   c. Validar longitud mínima de nueva contraseña
   d. Hashear nueva contraseña
   e. Actualizar password_hash en BD
   f. Configurar must_change_password = false
7. Usuario puede acceder al dashboard normalmente
```

```typescript
  updated_at: Date;
```

```typescript
{
  id: number;

  action: string;                       // 'tenant_created', 'login_success', etc.
```

```typescript
{
  id: string;                    // Formato: CMP-{timestamp}-{random}
```

## 📝 REGLAS DE NEGOCIO

### Formato de Teléfonos
- **Longitud:** Exactamente 10 dígitos
- **Formato:** Solo números (sin espacios, guiones, paréntesis)
- **Ejemplo válido:** `9233250673`
- **Ejemplo inválido:** `923-325-0673`, `(923) 325-0673`

### Procesamiento
- **Secuencial:** No hay procesamiento paralelo
- **Delay entre ambientes:** 5 segundos
- **Delay entre teléfonos:** 5 segundos
- **Reintentos:** Hasta 3 intentos con backoff exponencial

### Ambientes
- **PROD:** Ambiente de producción principal
- **QA:** Ambiente de pruebas (si aplica)

### Gestión de Tenants
- **Nomenclatura de BD:** `tenant_{nombre_lower_sanitized}`
- **API Keys:** Validadas automáticamente antes de crear tenant
- **Cifrado:** AES-256-GCM obligatorio para API Keys
- **Aislamiento:** BD separada por tenant (máxima seguridad)

### Seguridad de Contraseñas
- **Longitud mínima:** 8 caracteres (configurable)
- **Hashing:** Bcrypt con 10 salt rounds
- **Cambio obligatorio:** Primer login
- **Intentos fallidos:** 5 antes de bloqueo (configurable)
- **Tiempo de bloqueo:** 15 minutos (configurable)

### Limitaciones del API Movistar
- **Delay de datos:** 1.5 a 2 minutos para que los datos se reflejen
- **Rate limiting:** Muy estricto, requiere delays de 5 segundos
- **Timeout:** 30 segundos por request

## 🐛 PROBLEMAS COMUNES Y SOLUCIONES

### Error: "ENCRYPTION_KEY must be 32 bytes"
**Solución:**
```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
# Pegar el resultado en .env
```

### Error: "JWT_SECRET not configured"
**Solución:** Agregar `JWT_SECRET=tu_secreto_muy_largo_y_seguro` en `.env`

### Error: "Database does not exist"
**Solución:** Ejecutar `db/init.sql` en PostgreSQL

### Error: "API Key inválida" al crear tenant
**Causa:** La API Key no es válida para el endpoint de DN
**Solución:** Verificar que la API Key sea correcta y tenga acceso

### Error: "Tenant no encontrado" al validar
**Causa:** El token JWT tiene un tenant_id que no existe
**Solución:** Hacer logout y login nuevamente

### Cuenta bloqueada
**Causa:** 5 intentos fallidos de login
**Solución:** Esperar 15 minutos o que SuperAdmin reactive la cuenta

### Las validaciones no se guardan
**Solución:** Verificar que la BD del tenant existe (`tenant_{nombre}`)
